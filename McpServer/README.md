# OutlookAI MCP Server — Developer Documentation

The `McpServer/` folder contains the v3 layer of OutlookAI: a local **MCP (Model Context Protocol) server** that lets AI agents (Claude Code or any MCP client) search, read, show, and draft mail in classic Outlook — fast, offline, and without any cloud mail API.

This document is for contributors. User-facing documentation is in the [repository README](../README.md#mcp-server-mail-search-reading-and-drafting-for-ai-agents).

As of Phase 8 the server ships inside the add-in installer, and the add-in owns its Claude Code registration: opt-in for the user-global scope (kept correct on every Outlook start while it is on) and one-shot per project via `.mcp.json`. See [Deployment and registration](#deployment-and-registration) for the installed layout, the .NET 10 prerequisite, both scopes, and the developer path.

## Architecture

Two independent data paths, two processes:

```
MCP client (stdio JSON-RPC)
   │
   ▼
OutlookAI.McpServer.exe          net10.0-windows x64 console host - NEVER touches Outlook
   ├─ IndexSearch  ── OLE DB `Search.CollatorDSO` → Windows Search SystemIndex
   │                  (WS-SQL; ~10–100 ms per query; works with Outlook closed)
   ├─ EntryIdCodec ── decodes index item URLs (store UID, folder segments, /at= attachment parents)
   ├─ HitLocator   ── maps an index hit to a real Outlook item (see "load-bearing facts")
   ├─ Supervisor   ── bounds every COM call; kills and respawns the host on timeout
   │                  │  length-prefixed JSON frames over a named pipe
   │                  ▼
   │            OutlookAI.ComHost.exe    the killable COM child
   │                  └─ ComGateway ── ONE pumped STA thread owns ALL Outlook COM (late-bound dynamic)
   │                        └──► OUTLOOK.EXE  (read, show-me, drafts, send, freshness sweeps)
   └─ Audit log    ── structured line per write op, %LOCALAPPDATA%\OutlookAI\audit.log
```

**Why two processes.** A blocked outbound COM call cannot be cancelled - no timeout, no
token, no abort - and its RCWs cannot even be released, because `ReleaseComObject`
marshals into the same wedged apartment. An in-process timeout can therefore only make
the *caller* give up while the STA thread stays blocked forever holding Outlook
references. **The only way to reclaim a wedged COM call is to end the process that made
it.** On 2026-08-15 that gap turned an unresponsive Outlook into 1800 s of total silence
across 19 of 21 tools. Full rationale: [Docs/com-host.md](Docs/com-host.md).

Four projects:

| Project | Target | Contents |
|---|---|---|
| `OutlookAI.Core` | **net48 + net10.0-windows** | ALL domain logic: index search, EntryID codec, COM gateway/session, mail service, audit, health. Host-neutral — no MCP types, no console assumptions. The net48 target exists so a future in-Outlook (VSTO add-in) host can reference Core without a rewrite; it is CI-gated from day one. |
| `OutlookAI.McpServer` | net10.0-windows x64 | Thin host: [`ModelContextProtocol`](https://www.nuget.org/packages/ModelContextProtocol) SDK + stdio wiring + the tool attribute surface. stdout carries JSON-RPC; all logging goes to stderr. |
| `OutlookAI.ComHost` | net10.0-windows x64 | Both ends of the COM pipe: the killable child that owns the STA thread and every Outlook call, and the parent-side supervisor, session proxy and wire protocol. Published into the SAME directory as the server, so it costs ~163 KB rather than a second copy of the dependency set. |
| `OutlookAI.McpServer.Tests` | net10.0-windows | Three test tiers (below). |

Design rules (binding — see the code comments for the reasoning):

- **One STA thread owns all Outlook COM, in the child process.** It runs a real message pump and a COM `IMessageFilter` that retries `RPC_E_CALL_REJECTED` (a busy Outlook rejects automation calls). Index queries run in the PARENT on MTA threadpool threads and are parallel-safe - which is why search still answers from the index while Outlook is unreachable.
- **Every COM call is bounded, and the bound is enforced by `Process.Kill`.** 120 s for an ordinary operation, 90 s for a connect that may cold-start Outlook, 5 s for the health probe. On expiry the caller gets a structured `Timeout` error, the COM host is replaced, and the next call starts clean. The child deliberately has NO internal COM timeouts: it is not trying to survive a wedge, it is trying to be disposable during one.
- **`outlook_health` never joins the failure it reports.** It is asked precisely when Outlook may be unresponsive, so its COM probe is bounded at 5 s and degrades that one block rather than failing the report. It also carries a `comHost` block: mode, state, PID, restart count, last failure, and the frame-size measurements (`largestFrameBytes`, `frameLimitBytes`, `framesRefusedTooLarge`). A climbing restart count is the visible trace of Outlook wedging and being recovered from. The frame numbers answer a different question: an answer too large for one pipe message is refused rather than sent, and the high-water mark beside the limit is what says whether that limit is set anywhere near reality. Both counters are per server process and deliberately survive COM host restarts.
- **Nothing outlives its parent.** The COM host is held in a Windows job object with `KILL_ON_JOB_CLOSE` and additionally watches the parent PID, because a killed parent cannot run cleanup code. (18 orphaned server processes had accumulated on one machine before this existed.)
- **Core stays host-neutral** and keeps shared state under `%LOCALAPPDATA%\OutlookAI\` (audit log, attachment scratch dir) so future hosts can share it.
- **The server never kills or restarts Outlook.** It may *start* Outlook when a COM-requiring tool needs it — unless the add-in installer's `OutlookAISetup` mutex is held (returns a clear retry-later error instead). Always run non-elevated: an elevation mismatch breaks out-of-process COM attach.
- **Compact payloads everywhere.** Every list has a cap, every cap has a truncation/has-more flag, and the cap values are public constants on `MailService` pinned by T1 tests. Search over-fetches by one row so `truncated=true` means more matches definitely exist.
- **Near-zero destructive surface for mail.** The server can modify and delete exactly one thing: a draft it made itself. `update_draft` revises an unsent draft in a Drafts folder; `discard_draft` SOFT-deletes one (`Delete()` to Deleted Items — never `PermanentlyDelete`, never empties anything, never touches Deleted Items' contents) and only for drafts in the per-process `ServerDraftRegistry`, i.e. items returned by a draft tool of the SAME server process. Received mail, sent mail, anything outside Drafts and anything from an earlier session are structurally unreachable, and every refusal is explicit and audited rather than a silent no-op. Everything else is unchanged: no delete/modify tool for existing mail, moves are content-preserving and reversible, and the remaining writes are draft creation, attachment saves to the scratch dir, audit lines, and signature-file management (`manage_signature` — guarded by an ALWAYS-ON pre-modification backup, see below). `send` is a deliberate two-step flow (single-use content-bound confirm token, ~2 min TTL) with the sending identity hard-verified before transport.

## Tools

L1 search: `search` (always fresh; `exhaustive` flag), `thread`, `list_accounts`, `list_folders`, `list_signatures`, `manage_signature` · L2 read: `read` (body windows page via `body_offset`), `save_attachment` · L2.5 organize: `move_mail`, `archive_mail` (same-store, audited, reversible) · L3 show-me: `open_in_outlook`, `goto_folder`, `show_search_results` · L4 drafts: `new_draft`, `reply_draft`, `replyall_draft`, `forward_draft`, `update_draft`, `discard_draft` (each with optional `signature`, `cc`, `bcc`, `importance`, `request_read_receipt`, `attachments`; the three derived ones also take a `subject` override) · L5: `send` (high-friction, two-step) · diagnostics: `outlook_health` (21 tools total).

`manage_signature` creates, updates and deletes signatures by writing the signature file set under `%APPDATA%\Microsoft\Signatures` — always all three renditions (`.htm` UTF-8 + charset meta, `.txt` UTF-16 LE, `.rtf` derived ASCII), because each Outlook mail format reads only its own rendition and silently omits the signature when that file is missing. For create/update the caller supplies `body_text` and/or `body_html`; the missing renditions are derived. ALWAYS-ON safety: before ANY update or delete the signature's full current file set is copied to `%LOCALAPPDATA%\OutlookAI\signature-backups\<utc-timestamp>-<name>\` and the backup path is returned — a failing backup aborts the operation untouched. Deleting a signature also clears per-account default assignments referencing it, and the optional `set_default_for {account, scope}` records the signature as an account default (Outlook picks default changes up at its next start). Roaming-signatures caveat: on Microsoft 365 Apps 2303+ the cloud copy of signatures can overrule or revert local file writes unless `DisableRoamingSignatures=1` is set (`HKCU\Software\Microsoft\Office\<major>\Outlook\Setup`, where `<major>` is the Office version this machine actually has - see `outlook.officeVersion` in `outlook_health`); on Office LTSC (no roaming) the local files are authoritative. Every operation is audit-logged.

`list_folders` always returns the FULL folder tree in a stable traversal order (stores by display name, then depth-first with siblings by name), paged at 1000 folders per call via `offset`/`nextOffset` — real profiles fit in one page. **`truncated` means "not the whole tree", from either of two causes** (audit gap G3, closed 2026-08-18): more PAGES exist, in which case `nextOffset` says where to continue; or the WALK itself stopped at `FolderWalkAbsoluteCap` (10 000 folders) or `OutlookComSession.FolderWalkDepthGuard` (64 levels), reported as `walkCapReached` / `depthLimitReached`, in which case there is no `nextOffset` - paging cannot get past a walk cap, because the next call re-walks and stops in the same place, so the remedy in `advice` is to list one store at a time. It used to compute `truncated` from the already-truncated list, so the one truncation it could not see was the one that lost folders. `folderTotal` is a lower bound whenever either flag is set. **A store whose `DisplayName` Outlook will not report is listed rather than dropped** (gap G2): it appears under a `Com/StoreNaming` label, `(unnamed store N)` from its 1-based position in `Namespace.Stores`, with `nameUnreadable: true` beside it and a count in `storesUnnamed`. The label is deliberately not a guess at the real name (nothing derived from another property could round-trip, since a store scope is matched against the `DisplayName` that failed), so passing it back as `store` is refused by what it is, and a store-scoped listing reports what it could neither include nor rule out as `storesUnnamedExcluded`. The freshness sweep covers such a store under the same label and reports it as `sweep.storesUnnamed`; before this it abandoned the store at the failed name read and charged its four arrival-path folders to `foldersSkipped` and to no per-store bucket. `read` serves long bodies as windows: `body_offset` continues from the cached one-time extraction instead of re-transferring the body from the start. `list_signatures` enumerates `%APPDATA%\Microsoft\Signatures` (names + short excerpts for language detection) plus per-account defaults where the profile registry records them — absent values are reported as unknown, never guessed. **Draft composition (all four tools, rewritten in soak fix batch A).** Every draft is composed the way Outlook's own compose window does it, inside ONE held Inspector: `GetInspector` makes Outlook inject the account's own signature natively (new-mail or reply/forward rendition, HTML and embedded resources intact), the optional `signature` parameter then swaps that region by name via the `_MailAutoSig` bookmark dance (delete marker → `InsertFile` the chosen `.htm` → recreate the marker — what Outlook's own signature switcher and the add-in's `AITaskPane` do), the agent body REPLACES the empty draft region above that bookmark with the marker deleted and recreated around the untouched signature, and `Inspector.Close(olSave)` flushes the document into the item. The marker dance is load-bearing: Word absorbs text inserted at a bookmark's *start* into that bookmark, so writing the body at `Range(0,0)` while `_MailAutoSig` began at 0 made the whole message part of the signature region (the batch-A defect, live-proven in the saved HTML). If any Word step fails the composition falls back to the previous single wholesale `HTMLBody` assignment, so a draft is never lost or left body-less; the outcome reports `signatureApplied:false` and the audit line records `bodyPlacement=html`.

`cc`/`bcc` are **appended** to the recipients Outlook already put on the item (a reply-all's list is never replaced) and each address is resolved individually — unresolvable ones stay on the draft and come back in `unresolvedRecipients` instead of vanishing. **That list is capped at `MailService.UnresolvedRecipientsCap` (20) and, since 2026-08-18, says when the cap fired** - `unresolvedRecipientsTruncated` plus `unresolvedRecipientsTotal`, the has-more pair the RESOLVED recipient list two fields away has always carried, with an advice sentence naming the remainder. It used to `Take(20)` in silence, which matters more here than on the resolved list: the remedy for an unresolved address is to ASK THE USER about it, so an agent handed 20 of 27 as if it were the whole set never mentioned the other seven to anybody, and the draft carried a fault its own report had declared absent. The derived tools' `subject` override needs more than assigning `.Subject`: **live-proven on this build, Outlook REGENERATES `PR_CONVERSATION_INDEX` when `Subject` is assigned**, detaching the draft from its thread (`ConversationID` changes too). The shipped fix captures the `Reply()`-produced child index and the source's `PR_CONVERSATION_TOPIC` before the subject write and restores both through the `PropertyAccessor` (`0x00710102` binary, then `0x0070001F`) — both writes are accepted on an unsent draft, and the outcome reports `conversationTopicPreserved`. `importance` (`low`/`normal`/`high`) and `request_read_receipt` are plain item properties, validated pre-COM and echoed from the SAVED item.

**Revising and discarding drafts (soak fix batch C).** `update_draft` rewrites an existing draft in place through the same one-held-Inspector model, so only the draft region `[0, boundary)` changes and the signature plus any quoted original survive byte-identically. It deliberately has **no `HTMLBody` fallback**, unlike the creators: that fallback splices content in at the top of the body, which on an update would APPEND rather than replace, so a failed Word step closes the inspector with `olDiscard` and refuses the whole call — a refusal the agent can retry beats a silently duplicated body. **Recipients are REPLACE, not append** (the opposite of the creators' `cc`/`bcc`): on creation "append" is the only sane reading because Outlook has just filled the list itself, but on a revision the caller states the final list, and there would otherwise be no way to REMOVE a recipient — so passing the full list is how you add one, and an omitted list is left untouched. A subject change carries the same `PR_CONVERSATION_INDEX`/topic restore the derived tools use. **Attachments are ADD**, with an explicit `remove_attachments` name list; remove+add of one name in a single call is a replace. **Additions run FIRST** (changed 2026-08-19) and removals then delete the N lowest-indexed instances of each name, counted before anything was attached - `Attachments.Add` appends, so those are exactly the pre-existing copies. The order is the cheap half of surviving an interruption: with removals first the window between the two steps is a draft that has LOST the user's file, and with additions first it is a draft that has a duplicate. `discard_draft` is the only mail-deleting tool in the product: soft delete only, gated on all three of (in the session registry) AND (in a Drafts folder) AND (unsent), and its result carries `newEntryId` + `fromFolder` so the discard is reversible with `move_mail` exactly like any other move.

**`update_draft` is RE-ENTRANT (2026-08-19): repeating an interrupted call FINISHES it rather than performing it twice.** One contract method is not one COM call - `TryUpdateDraft` is ~20 sequential cross-process calls with no transaction, and the operation deadline kills the COM host BETWEEN two of them far more often than inside one, skipping every `finally` block written to leave a draft untouched. Three pieces make a repeat safe:

- **The intent record lives in the PARENT** (`Services/DraftUpdateIntents`), because the parent is what survives the kill. It is in-memory and unpersisted, exactly like `ServerDraftRegistry` and `SendConfirmationTokens`: a restarted process never observed the draft and must not claim it can complete an update it cannot vouch for. It is deliberately NOT a property on the draft - such a marker can only be written by the process that dies, so it would be exactly as unreliable as the thing it records, it needs a second mutation to clear, and it puts server bookkeeping on the user's own mail.
- **The idempotence key is DERIVED, not supplied** (`DraftUpdateIntents.KeyFor`): SHA-256 over the draft id plus every argument that reaches Outlook. The send path's confirm token is caller-supplied because its purpose is friction; re-entrancy's purpose is the opposite - it has to work when the caller does nothing special. Two identical calls are not automatically a retry: only a request whose outcome is still UNKNOWN is resumable, a call that answered settles its record, and any other update to the same draft drops it.
- **The record holds a PRE-IMAGE, not a progress log**, because progress is knowable only to the process that died. What is recorded is the draft's attachment names and its `PR_CONVERSATION_INDEX`/topic BEFORE anything was applied, and the repeat converges on the requested END STATE from whatever it now observes (`Com/DraftAttachmentPlan`). That is correct whether or not a partial attempt persisted - which matters, because Microsoft documents neither outcome. The conversation index is the half that cannot be recovered any other way: assigning `Subject` regenerates it, so a repeat reading it live would restore the value the interrupted attempt had already destroyed.

The pre-image costs at most two extra reads, taken only when the request contains something a blind repeat could get wrong (a subject change, or files to attach); it doubles as the store resolver, so a bare EntryID in a non-default store is now found by a READ rather than by offering the mutating call to each store in turn. An interrupted update writes `update_draft_outcome_unknown` to the audit log and tells the caller to re-issue the exact call - the inverse of what every other killed mutation is told, and the point of the work. A resumed call reports `resumed: true` with advice saying the fields listed are the end state it converged on.

**Signature images are EMBEDDED, not linked (D47).** Word's `Range.InsertFile` — the only HTML-into-Word verb this codebase uses — does not embed a signature's pictures: it inserts each one as a LINKED `InlineShape` pointing at the file under `%APPDATA%\Microsoft\Signatures\<name>_files\`, and Outlook stores that link verbatim, so a composed draft carried `<img src="file:///…">` and **zero attachments**. It rendered only because the file sat on the same machine, and re-rendering the document (exactly what `update_draft` does) made Word re-serialize the link as its VML placeholder AutoShape — the `<img>` vanished. Every composition therefore embeds its linked pictures before committing (`LinkFormat.SavePictureWithDocument` then `BreakLink`, on the create and the revise path), which makes Outlook write a real `cid:` reference backed by an inline attachment: it survives any number of re-renders and, unlike a `file:///` link, reaches the recipient. **Residual limitation:** a draft composed by an older build already holds the link in its stored HTML, and by the time the `WordEditor` is available Word has degraded it to a placeholder — nothing in the update path can rescue it. That case is reported (`inlineImagesDropped` + `inlineImagesAdvice`, and an audit field), never silent, and re-supplying `signature` on the update restores the image in embedded form.

**Attachments on drafts.** All five draft tools take `attachments` (absolute paths; no directory restriction by design). Validation is PRE-COM and **fail-closed for the whole set**: if any entry is missing, unreadable, empty, a duplicate or a directory, nothing is attached, no draft is created or changed, and the error names EVERY offending path with its own reason — one retry fixes everything, and a mail that silently misses a file the agent believes it sent is never produced. Caps: 20 files, 150 MB per call. What comes back in `attachments` is read from the SAVED item, not echoed from the request. **Security interlock:** the send confirm-token's content hash covers the attachment set (name + size, order-insensitive) *and* a SHA-256 digest of the HTML body, so adding or removing a file after a token was issued invalidates it — and so does a markup-only edit, which matters because Outlook derives `MailItem.Body` from `HTMLBody` lossily: retargeting a hyperlink while its visible label stays leaves the plain text byte-identical, and a body-text-only hash could not see it. The digest is measured to be stable across independent snapshots of an untouched draft, so it cannot cause spurious `draft_changed` refusals.

**The user's writing rules arrive in a rejection, never in the schema.** The add-in lets a user edit the prompts OutlookAI sends, and those rules can be pages long and can change between two tool calls. A tool description cannot carry them: `[Description]` arguments are compile-time constants, and Claude Code cuts a TOOL description past 2048 UTF-16 code units - measured, not inferred; see Docs/magic-numbers.md - the 859-character directive that used to ride on `body`/`body_html` pushed those descriptions to 2102 characters, so it sat past the cut and was plausibly never delivered. So the first call to any drafting tool **that supplies `body` or `body_html`** is refused with `error.type = "WritingRulesRequired"`, carrying the user's `Preamble` section verbatim in a new `error.writingRules` field plus what to do about it; the agent composes again and the retry proceeds. The gate is keyed to a hash of the rules text (normalised for line endings by the store's own comparison rule, so a trailing newline is not an edit), so editing the rules re-arms it and the change reaches the very next call rather than the next session. An `update_draft` that supplies no body - recipients or attachments only - is never gated. The check runs **before any COM work**, which makes the refusal instant, keeps it working with Outlook closed, and is what lets a CI-tier test exercise it. An unreadable registry **fails open**: losing the rules must never cost the draft.

Three consequences for contributors. `Services/PromptDefaults.cs` and `Services/PromptStore.cs` are compiled into `OutlookAI.McpServer` (the tests reach them through `InternalsVisibleTo` and must NOT re-link them - one public type in a linked file compiled into two assemblies is CS0436, an error here). Any T3 test that calls a draft tool with a body must call `client.PrimeWritingRulesGateAsync()` first, or it will assert against the gate's refusal instead of the behaviour it meant to test. And `Services/AddInServerContract.cs` - the single definition of every registry key, value name and config property the add-in and the server exchange - is linked into `OutlookAI.Core` and into the test project, must stay `internal`, and must NOT be linked into `OutlookAI.McpServer` for the same CS0436 reason.

`move_mail` moves 1–50 items (hit ids or EntryIDs) to a store-relative folder path, **same-store only** (v1 restriction: each item moves within the store it lives in; a requested `store` that differs from an item's own store fails per-item — archive semantics are same-store and EntryIDs are store-scoped). `create_folder: true` creates missing target segments as mail folders. Refused targets: Deleted Items and its subtree (moving there is deletion semantics — the server has no delete surface), the Outbox, non-mail folders, and the item's current folder. `archive_mail` moves each item to ITS OWN store's **designated Archive folder** — the folder Outlook's own Archive action (Backspace), mobile swipe-archive and OWA use. Resolution is localization-proof and never guesses by name: primary = `Store.GetDefaultFolder(39)` (an undocumented `OlDefaultFolders` value the live build honors; the resolved folder is verified — same store, mail folder, not a core default folder — before use), fallback = `PR_IPM_ARCHIVE_ENTRYID` (0x35FF0102) on the store object; a store with neither fails per-item and nothing is created. Both tools are content-preserving, per-item audited (`op=move_mail`/`op=archive_mail` with from→to) and reversible: every result carries `fromFolder` plus `oldEntryId`/`newEntryId` — undo = `move_mail` with `newEntryId` and `folder = fromFolder`. **EntryIDs change on ANY move**: the moved hit id keeps resolving within the session (its cache is refreshed to the new EntryID), other stale ids/index rows surface the standard re-run-search error until the index catches up.

Search behavior (there is no mode parameter): every search merges the index results with a bounded COM sweep for mail newer than the index frontier, so just-arrived mail is always found. **The sweep follows the search scope** (soak fix 13): with `folder` set it covers that folder *and its subfolders* unless `include_subfolders: false` narrows it to that one folder (soak fix 15 - the flag is honored by all three tiers and is part of the sweep cache key; bounded at 40 folders), otherwise it covers the four arrival-path default folders — Inbox, Sent Items, Deleted Items, Junk Email — of the store(s) in scope. Measured on the dev machine across 5 stores: 86 ms for the old Inbox+Sent pair, 135 ms for all four, versus ~10 ms per folder for a full walk of 41-46 folders per store (which is why the default set is fixed, and why mail a rule files into a custom folder needs `store` + `folder` until the index catches up). The `sweep` block of the response reports the scope descriptor, the folder count and — while the list is short — the folder names. **`sweep.scopeShape` is that descriptor as a token software can branch on** (audit gap E2, closed 2026-08-18): `default_folders`, `folder` or `folder_only`, rendered from the same `MailService.ClassifySweepScope` decision that produces the `sweep.scope` sentence, so the two can never describe different breadths. It exists because the shallow four-folder default is the likeliest remaining coverage hole in ordinary use - a server-side rule that files mail into a subfolder before the indexer reaches it leaves that mail in neither tier - and the only way to detect it was to compare `sweep.scope` against an English sentence. It deliberately raises no coverage code and never sets `degraded`: this shape holds for nearly every search anyone runs, and `ClassifyFreshness` derives `partial` from the code list, so a code here would mark almost every answer degraded and blunt the flags that fire rarely (the `sweep.attachmentTextCovered` precedent). Both fields are absent together on a sweep that was refused or could not run - "it covered the default folders" is a claim about coverage, and those paths covered nothing. The sweep may autostart Outlook headless; its result is cached for ~10 s, keyed on the index frontier **plus the store scope, the folder scope and `include_subfolders`** so a narrow or shallow sweep can never answer a broader or recursive query. When the sweep cannot run (installer mutex held, COM attach failed, Outlook cannot start, folder not openable) the search still succeeds with index-only results plus a freshness warning in `advice` — a search never fails because of the sweep. **Partial coverage is now reported in fields, not only in prose:** `degraded: true` means "not fully fresh" and travels with `freshness: "index-only"` when the sweep did not run, or `freshness: "partial"` when it ran and covered less than its scope, with `sweep.coverageGaps` naming which of thirteen holes fired (`no_index_frontier`, `nothing_swept`, `folders_failed`, `folder_cap`, `sweep_time_budget`, `time_budget`, `depth_limit`, `folders_skipped`, `item_cap`, `item_cap_unsorted`, `rows_unreadable`, `filter_unreadable`, `body_cap`). `item_cap` and `item_cap_unsorted` are one cap with two meanings (audit gap H2, closed 2026-08-18): the per-folder cap keeps the NEWEST 200 of a folder's window, which is what makes "the oldest is what is missing" actionable, but `Table.Sort` can fail and that failure used to be swallowed. The sweep now reports whether each capped folder was actually sorted, `sweep.itemCappedFoldersUnsorted` names the ones that were not, and each advice sentence is generated from the split so it names only folders it is true of - the unsorted one says the cap kept an arbitrary 200 and that which mail is missing is unknown. **`sweep_time_budget` is the sweep running out of its OWN time, and expiry is now an answer rather than a failure (2026-08-19).** The sweep is bounded twice: `MailService.SweepBudgetMs` (180 s) is the gateway deadline above it, and `MailService.SweepWorkBudgetMs` (165 s, derived as that minus the return trip) is the budget the walk itself measures against its own clock inside the COM child. Until this existed the whole-profile sweep had no budget of its own, so a sweep that ran long raised a `TimeoutException`, the supervisor concluded the COM host was wedged, killed and replaced it, and **every folder already swept was discarded** - a large mailbox lost its freshness tier entirely instead of getting part of it. That was observed on a real profile, and it is measured: on a 20,000-item unindexed PST with the per-folder cap engaged, one store's sweep takes ~12 s (13.6 / 11.8 / 10.7 / 11.9 s over four runs), so a five-store profile extrapolates to ~60 s against the old 30 s budget. The walk now checks the budget at every store and every folder boundary, stops there, returns what it covered, and raises `sweep_time_budget` with `freshness: "partial"` and `degraded: true`. It is a separate code from `time_budget` because the remedies point in opposite directions: `time_budget` is the folder-scoped subtree walk hitting its own 2 s bound and says scope narrower or pass `include_subfolders: false`, while this one says the PROFILE is big and the remedy is to name a store or a folder. The flag is deliberately NOT attributed per store - the budget is spent across every store the sweep visited, and the stores it never reached are exactly the ones with no per-store entry to attribute it to, so a store-scoped request would otherwise read its own zero coverage as "nothing was there". **The supervisor no longer counts this as evidence that Outlook is unresponsive** (`ComHostPolicy.TimeoutIndicatesUnresponsiveness`): a caller that hands the gateway its own budget is stating how much of its work it will pay for, and two ordinary slow searches used to open the circuit breaker and fail every COM request for 30 s with nothing wrong but the size of the mailbox. The unqualified class deadlines still count. The higher budget is also what makes the body bound below load-bearing: the 432 KB frame high-water previously measured on a real profile was bounded by the old 30 s timeout, not by any item cap, and the same corpus measured 10,734,599 bytes from a single store's sweep once it was allowed to finish - five such stores extrapolates to ~54 MB against the 64 MB frame limit. **`body_cap` is the sweep's own body bound, and it is the only cap in this server applied on the COM side of the pipe** (maintainer decision 2026-08-18: cap bodies at the COM layer so a frame that cannot be sent cannot be built - `MaxFrameBytes` was deliberately not moved and the sweep result was deliberately not chunked). One sweep answer is ONE frame; the sweep reads the FULL body of every item it finds; and `BodyCharsDefault`/`BodyCharsCap` are applied in `MailService`, on the far side of that pipe, so they bounded what an agent sees and never what crosses. Each swept body is now cut at `OutlookComSession.SweepBodyCharsCap` (500 000 characters, which IS `read`'s hard body cap), and one sweep carries at most `OutlookComSession.SweepBodyBytesBudget` (32 MiB, half the frame) of body text in total - the per-item cap cannot bound the frame on its own, because the item count is 4 folders x 200 x every store in the profile, and it exists to keep the budget fair rather than to bound it. **A cut is not a display truncation.** These bodies are matched against and shown to nobody, so unlike `read`'s windowing - which pages and therefore loses nothing - a term appearing only past the cut in just-arrived mail is not matched. So `sweep.itemsBodyCapped` counts the cut items, `sweep.itemsBodyCappedUnmatched` counts the subset that then failed the term match, and **only that subset raises `body_cap`**: a cut body on an item that matched anyway cost the answer nothing, and a code firing there would blunt the codes that fire rarely. `sweep.bodyBudgetExhausted` says which bound cut, because the remedies differ - read one enormous mail (its body pages via `body_offset`), or narrow the search so fewer items are swept. The advice says "may be" rather than "is", because settling whether the term really sat past the cut needs exactly the text the bound refused to carry. Counts are taken inside the store filter, so a cached all-stores sweep never reports another account's cuts, and a cut body never reaches the read-path body cache: that cache is fed only by `read` itself, so a `read` of such a hit still returns the whole body. `folders_skipped` means folders that EXIST and could not be opened or enumerated: a default folder the store simply does not have is not a gap, raises no code and does not degrade the search, and is reported separately as `sweep.foldersAbsent` (present only when non-zero), so the four-folder default scope reconciles as `foldersSwept + foldersSkipped + foldersAbsent`. That distinction rests on `Store.GetDefaultFolder` returning null for an absent folder rather than throwing; a thrown failure is never read as absence, even when its HRESULT looks like one, because misreading a failure as absence would silently drop a folder whose mail really is missing. **Coverage is attributed per store**: a cached all-stores sweep serving a store-scoped request reports that store's own swept/skipped/failed/absent counts, so a search of one account can no longer be degraded by a folder another account could not open, and a store the sweep never reached reports zero coverage rather than the totals. A sweep that was not NEEDED - the requested window ends before anything newer could exist - is reported as `sweep.notNeeded` with `freshness: "live"` and no degradation, which is distinct from one that could not run. **One exception, and it is the whole of `no_index_frontier`:** "not needed" claims the INDEX already covers the requested window, which is false over a store the index holds no mail for, so such a search reports `freshness: "partial"` and `degraded: true` instead. That code is raised by the index tier rather than by the sweep, so it survives a sweep that was not needed, was refused (a `to` filter or an attachment-only search) or failed outright - all three name the stores involved in `sweep.storesWithoutIndex`, taking the profile's store list from Outlook when there is no sweep result to read it out of.

**Freshness is measured per store when the search names one.** `staleness.newestIndexedUtc` is that store's own index frontier, matching what `outlook_health`'s per-store probe reports; it stays profile-wide for an unscoped search and for `exhaustive`, which resolves no index scope by design. Store level rather than folder level is deliberate: the frontier is an INGESTION frontier and only approximates one where mail arrives, so scoping to a quiet folder would open a window years wide and read 200 already-indexed items in every folder it touched. Store level is self-balancing - a quiet store has a wide window with little in it. **An unscoped search opens one window PER STORE** (audit gap E1, closed 2026-08-18): each store's window starts at its own index frontier, so a quiet account is no longer swept back only as far as the busiest account's clock. Measured on the dev machine: 33-39 ms added per unscoped search on a two-store catalog, against frontiers 11 min 19 s apart - i.e. the single profile-wide window was eleven minutes short for one store, every time, silently. A store the index catalog does not know gets the widest window (`EmptyIndexSweepWindow`) rather than the profile frontier, because it is the one store whose gap is unmeasured, and `sweep.gapStartUtc` reports the widest window the sweep actually opened rather than the one it planned. Those codes drive the advice text rather than sitting beside it, so a code without a sentence fails the build. Before this, a partially covered sweep reported `freshness: "live"` and no degradation while the advice said coverage was incomplete - so an agent reading fields, which is the sensible way to read a payload, was told a partial answer was whole. **The exhaustive scan has a deadline class of its own since 2026-08-19** (`ComHostOperationClass.ExhaustiveScan`, 615 s, from which `MailService.ExhaustiveTimeBudgetMs` derives 600 s by reserving the return trip). It is the one mode a caller picks BECAUSE completeness matters more than speed, and the one operation whose budget expiry is a documented answer rather than an incident - so it is allowed to be long, while every other tool keeps the ordinary 300 s hang detector. Raising the shared deadline instead would have made `read`, `new_draft`, `list_folders` and `move_mail` each wait 10.25 minutes before a wedged Outlook is reclaimed, and over 20 minutes for the breaker to open. The old 105 s was the binding constraint on completeness rather than a backstop: measured on a real profile, a 60-day whole-store scan reached 3 folders of 32 before it expired. `exhaustive: true` instead runs a folder/date-bounded COM scan that bypasses the index entirely (requires `store` plus `folder` and/or `after`; whole-word matching on subject+body, no attachment content; a `folder` bound follows `include_subfolders` like every other mode, so pass `include_subfolders: false` to keep a big subtree inside the 600 s budget - `foldersScanned`/`foldersSkipped` and `advice` report partial coverage honestly). **Its folder walk is depth-bounded since 2026-08-18** (audit gap F4): it was the one walk over Outlook's folder graph with no bound at all, so a cyclic or pathologically deep tree was an uncatchable `StackOverflowException` that ended the COM host process and reached the caller as "Outlook has gone away". The guard is `OutlookComSession.FolderWalkDepthGuard` (64), the same comparison the sweep walk and the listing walk already make, and it bounds only the offending subtree so sibling accounts are still scanned. Hitting it is NOT silent: the stop latches on the scan state, crosses the process boundary on `ComExhaustiveResult`, and reaches the payload as `exhaustive.depthLimitReached` plus the sweep's own `depth_limit` code in `exhaustive.coverageGaps`, with `freshness: "partial"` and `degraded: true` - replacing a crash with a silent truncation would have been the worse trade in the one mode a caller picks BECAUSE completeness matters. **Its result cap counts CANDIDATES, not results** (audit gap F3, closed 2026-08-18): `maxItems` is `top` and it stops the folder walk on items the DASL filter matched, while `from`, `unread_only` and `has_attachments` are read off the returned snapshots and applied afterwards - so a scan can stop at 25 candidates, discard 24 of them and hand back one result with `truncated: true`, while thousands more match further into the tree. `exhaustive.postCapFilters` names the filters that ran after the cap, `exhaustive.itemsFilteredOut` counts what they removed, and the pair raises `post_cap_filter` in `exhaustive.coverageGaps` when the cap actually fired - only then, since without the cap the filter saw the whole matched set. The remedy the advice gives is a tighter folder or `after` bound rather than "raise top", which is capped at 100. **Since 2026-08-19 the scan is RESUMABLE (audit gap F2), which is what makes that cap tolerable.** The mode exists for when the index is stale/broken or correctness beats speed.

**The resumable exhaustive scan, and why it is shaped the way it is.** F2 was the worst row left on the gap map: the walk imposed no order, so when `maxItems` or the time budget stopped it what was missing was WHOLE FOLDERS nobody opened, chosen by whatever order Outlook's `Folders` collection happened to return - honestly reported and completely unactionable. Measured on a real Exchange profile, a 60-day whole-store scan reached **3 folders of 32** because one is a 108,144-item archive at roughly 12 items/s; on a local PST the same walk runs at roughly 1,200 items/s and `top` stops it instead. **Same token, two stop reasons, different remedies**, which is why `exhaustive.stopReason` is RECORDED by the walk (`complete` / `time_budget` / `result_cap`) and never derived afterwards from `truncated` and `timedOut` - both can be true and only one ended it. `depthLimitReached` can never be a stop reason at all: the depth guard bounds one subtree and every sibling branch is still walked.

*Order first, because a continuation is only as correct as the order it resumes into.* Microsoft documents no ordering for `Folder.Folders`, so the order exists only because this code imposes it. `ExhaustiveScan` now runs an **enumeration pass** over its scope (structure reads only, depth-guarded, deadline-checked) using the SAME sibling comparator `list_folders` promises - `OutlookComSession.CompareSiblings`, name `OrdinalIgnoreCase` then collection position, shared by all three legs rather than copied (the store-ordering leg was a third copy until this pass) - and then walks that ordered list, opening each folder by EntryID. The pass buys three things one combined walk cannot: an honest `position.foldersTotal` even when the scan covered four folders, index arithmetic instead of recursion state, and the only vantage point from which "a folder appeared BEFORE the cursor" is visible.

*The token.* A stop returns `exhaustive.nextToken`, a `scan-<32 hex>` handle costing about ten tokens of context; the walk state behind it lives in `Services/ExhaustiveScanCursors` **in the server parent, never in the COM host child** - the event this exists for is a scan past its deadline, which ends with the supervisor killing that child, so state kept there would be destroyed by exactly the failure it must survive. Per-process and unpersisted, on the same rule as `SendConfirmationTokens`, `ServerDraftRegistry` and `DraftUpdateIntents`: a restarted process never ran the earlier pages and must not claim it can continue one. TTL 30 min (about 2x `ExhaustiveScanDeadlineMs`, T1-pinned as a RELATIONSHIP - a TTL shorter than one page is unusable by construction), 4 concurrent chains, `MonotonicClock`. Every page issues the next token and supersedes the previous one. What the token does NOT need to carry is survivability: `exhaustive.position` reports the resume folder and date in plain fields, so an expired token or a restarted server costs nothing - the caller continues by hand with `folder` and `before`, which already exist.

*The ladder, per folder, reported as `position.resumeTier`.* **`date`** - the table sorted, so resumption is a narrower DASL restriction (`datereceived <= cursor`, inclusive, plus the tie set of ids already returned at that instant) and nothing depends on row order; the skip costs nothing because the provider folds it into the query it was going to evaluate anyway. **`ordinal`** - the sort was refused, so the position is `GetArray(k)` (the only bulk skip `Table` offers; there is no seek-to-row-N and `FindRow` always restarts) plus a **watermark EntryID** checked after the skip, because MAPI documents that an unsorted table has no guaranteed order and that its rows are live; a mismatch REPORTS (`resume_position_lost`) and falls to the next rung rather than resuming somewhere it cannot vouch for. **`restart`** - the folder is re-read from the top with per-folder EntryID suppression (capped at `ScanCursorEmittedIdCap`, and at the cap suppression STOPS and says so via `dedup_capacity` rather than dropping rows). Every rung returns the same mail; which one pays is a cost, and it is also evidence - `date` on a folder means `Table.Sort` works there.

*Tree motion is detected, not assumed.* The finished-folder set is EntryIDs (`PidTagEntryId` is long-term, so a rename or a within-store move preserves it; a cross-store move changes it and reads like a deletion, handled the same way) and it is reconciled against a fresh enumeration on every page. A folder in scope that is neither finished nor the cursor and sorts BEFORE the cursor appeared since the token was issued - it is SCANNED, not skipped. A finished folder no longer in scope left. The cursor folder itself vanishing is the one case that loses mail, and it is named as such. All of it raises `tree_changed`.

*What deliberately did not change.* `top` stays at 100 and counts **per page** - `exhaustive.itemsReturnedTotal` is the running chain total, so the accumulation an agent is paying for is visible rather than discovered afterwards. `result_cap` and `time_budget` keep firing on a resumable stop, and `degraded: true` / `freshness: "partial"` stay set: **the token is a remedy, not a repair**, and suppressing the flag because a remedy exists is exactly the "looks complete and quietly is not" failure the coverage-code system was built against. A page reached via a token raises **`scan_resumed`**, which is what stops the LAST page of a chain - which by itself covered everything it was asked for - from reporting `freshness: "live"` to an agent that would relay it as a finished search. A resume whose other arguments differ is **refused**, with the changed argument named; `top` and `snippet_chars` may differ per page because they shape a page rather than the question. A superseded token is refused too, with the chain's position in the message, because honouring it would suppress exactly the rows the replay exists to return.

*Where the prose lives.* Nothing new went into the `search` tool description: it is at 1791 of the client's measured 2048-UTF-16-unit cut, the cut is per string with no per-tool bucket, and 257 units is not a paging contract - spending them would put `DEGRADED RESULTS` one edit from being truncated again. The contract is on the new `resume_token` parameter's own description (parameter descriptions are measured by `DescriptionBudgetCiTests` and are not cut by the client), the `exhaustive` parameter gained one clause, and everything about a particular answer is in the payload and its `advice`, which are uncapped. **Delegate/shared mailboxes are indexed FLAT** - a subfolder is stored under the delegate name and its own name only, with the intermediate folders dropped - so a delegate `folder` scope is resolved as the delegate mailbox root plus folder-NAME matching (before soak fix 15 the server built a nested delegate URL that does not exist and every delegate subfolder search returned zero rows, silently). Three consequences are reported in `advice` and the response `scope` block rather than hidden: a subtree that cannot be expressed as a folder-name list widens to the whole delegate mailbox, a mailbox holding two folders with the same name can over-return, and, since 2026-08-18 (audit gap G4), a folder-name list built from a COM walk that hit its own bounds is flagged as `scope.folderNamesTruncated` with `degraded: true`, because in a flat namespace a folder name the walk never reached is a folder no tier looks in, and `scope.folderNamesMatched` is a count that reads identically either way. The scope predicates are unchanged by that flag: narrowing further would drop mail and widening would answer with the whole delegate mailbox under a folder scope the caller chose. A folder search whose INDEX TIER returns nothing re-checks whether the folder path resolves in the index at all, and reports it as `index.folderNotIndexed: true` plus an advice sentence when it does not (audit gap G5, closed 2026-08-18). It used to run only when the MERGED answer was empty, so one item the freshness sweep returned silenced it - and that item comes from COM, where the folder resolved perfectly well, so it said nothing about the question being asked. The state it hid is the ordinary one for a renamed or localised folder: the sweep answers for the last few minutes, the index answers for nothing, and the whole thing reads as a thin result set. It does not set `degraded`, because the two TOP-1 probes cannot distinguish a path that does not resolve from a folder created this morning whose mail is all still inside the sweep window.

**What counts as a searchable item is now ONE rule, in one place** (audit gap B3, maintainer decision 2026-08-18: *"unify all three, and prefer returning EVERYTHING where possible"*). The rule is `Core/Mapi/MailItemAdmission.cs` and it is that **an item's CLASS never excludes it** - what bounds a search is the folder it looks in. Before this the three tiers admitted three different sets and nothing in the payload said so: the index tier required `System.Kind` to contain `email`, the freshness sweep filtered nothing, and the exhaustive scan filtered `PR_MESSAGE_CLASS like 'IPM.Note%'` — so one query returned different items depending on which engine answered, a meeting request the sweep returned today vanished once it was indexed, and the mode that exists FOR completeness was the only one blind to NDRs and read receipts. Bounce reports, read receipts, meeting requests and responses, posts and sharing invitations now come back from all three. An allowlist of "mail-ish" classes was considered and rejected on the fact that decides it: the SystemIndex carries no message-class column, so an allowlist could only ever have been enforced in the COM tiers, replacing one asymmetry with another. **What each tier still cannot reach is reported rather than implicit:** the COM tiers (sweep, exhaustive scan) only enter folders whose `DefaultItemType` is `olMailItem`, which is unchanged and is not a class filter; the index tier has no folder-type column and no message-class column, so its widening also admits items of folders the COM tiers never open — over-return, which a caller can see and filter, rather than under-return, which nothing downstream can detect. How far that reaches depends on the statement: an UNSCOPED search still carries `IndexRowFilter.UnscopedKinds` (the provider needs it to stay off the file system), so it gains message-level `calendar` rows — meeting requests in the Inbox and appointments in the Calendar alike — and nothing else; a store- or folder-scoped statement emits no kind predicate at all, so in that store a contact, a task or a note can now surface too. Widening the SQL narrowing to prevent that was rejected: the enumerated kind list is not future-proof, and re-applying it under a scope would re-open the 22.6%-of-attachment-rows recall hole that removing it closed.

**That over-return can never COST mail** (`Core/IndexSearch/IndexOrderGuard.cs`). The rows the widening lets in are the ones with no `System.Message.DateReceived` - appointments, contacts, unsent items - and the statement is `SELECT TOP n ... ORDER BY System.Message.DateReceived DESC`, applied by the provider BEFORE the cut. Where Windows Search sorts a NULL under `DESC` is not documented and has never been measured here, so if NULLs sort first those rows fill the `n` and every real mail behind them stays at the provider: a full page of appointments, nothing short, nothing dropped, nothing to notice. The guarantee shipped instead of the assumption is that **a row the index cannot date can never reduce the number of dated rows a search returns**, and it holds under any collation. Two things could take a slot and both are closed: the client-side trim now orders rankable rows first and unrankable ones last before trimming (the same "undated last" convention the merged hit list already used), and where the statement was TRUNCATED with an unrankable row in it - the only case a client-side ordering cannot fix, since the missing rows never arrived - the same statement is re-run with one added predicate admitting only rows that carry the ordering column, and the two answers are unioned. The refetch is conditional, so a NULLs-last provider never pays for a second statement, and a search carrying `after`/`before` never triggers it at all (a date predicate already excludes undated rows). If the recovery query itself fails, the answer is still returned and flagged with `index.candidatesExhausted` rather than silently short. A DATED meeting request or bounce report can still push an older mail off the end of a `top` list: that is the admission decision working, not displacement.

Every hit that is not ordinary mail carries **`itemClass`**, and only then, so the field is absent from the overwhelming majority of hits and its presence is itself the signal. Two vocabularies, deliberately: a hit from Outlook (`source` `live`/`exhaustive`/`com`) carries the real MAPI class (`REPORT.IPM.Note.NDR`, `IPM.Schedule.Meeting.Request`), while a hit from the index carries `kind:<System.Kind>` (`kind:calendar`, `kind:unknown`) because that tier never opens the item and a bare class name would claim an authority it does not have. One `advice` sentence names the count and the classes when an answer holds any, so an agent does not relay "four mails about the invoice" over a list containing a delivery receipt. The count of what each tier REFUSED surfaces too: **`index.rowsScanned` / `index.rowsDropped` / `index.candidatesExhausted`** (the last of these closes gap G6 — it used to be advice-only) on a non-exhaustive search, and `exhaustive.rowsDropped` / `exhaustive.rowsUnreadable` on an exhaustive one, where the difference between the two was exactly this class filter and is now zero by construction. `KindFilter` was renamed with the rule — `MessagesAndAttachments`, `MessagesOnly`, `AttachmentsOnly`, plus `MailKindOnly`, which only store-scope discovery uses — because member names carrying the old narrowing would be the same defect one level down.

**`staleness.oldestStoreFrontierUtc`** (Q7a) sits beside `newestIndexedUtc` and answers the question a maximum cannot: how far behind is the WORST store in scope. `newestIndexedUtc` stays a profile-wide maximum on an unscoped search precisely so `search` and `outlook_health` never report different numbers for the same profile; the new field is that store's own frontier on a store-scoped search (one store in scope, so both fields agree) and the earliest per-store frontier on an unscoped one. It is ABSENT when no per-store frontier was measured — an exhaustive search, or an unscoped search whose store catalog could not be read — and absence means "not measured", never "no lag". **`sweep.storesWithoutIndex` is capped** at `MailService.UnindexedStoreListCap` (12, derived from `SweptFolderListCap`) with `sweep.storesWithoutIndexTruncated` and `sweep.storesWithoutIndexTotal` beside it (Q7b); the `no_index_frontier` advice sentence names the cap and the remainder too, because capping the payload alone would have left the whole list in the prose an agent relays to the user.

**A `store` scope is resolved against the profile OUTLOOK has, not against the index** (audit gap A4, closed 2026-08-18). Store scope used to be looked up in the index's own catalog - a list derived by sampling indexed item URLs - so a store the local index holds nothing for could not be scoped to at all, and every non-exhaustive `search` naming it failed with `Store 'X' was not found in the local index. Known stores: ` (an empty enumeration, whose suggested remedy was `list_accounts`, which returns the name that had just failed). That is the ordinary state of a PST, an archive-only data file, a fresh install, a machine where indexing is off or excluded by policy, or one still building its index - and it was worse than the unscoped case, which has always degraded gracefully and said so. The lookup now falls through to the COM store list (the same one `list_folders` refuses an unknown store against, and from the same five-minute cache, consulted only when the index lookup found nothing, so an ordinary search pays nothing for it), which splits the two cases that used to share one message: a store the profile HAS searches normally with the index tier SKIPPED - `index.storeNotIndexed: true`, `scope.shape: "store_not_indexed"`, `sweep.storesWithoutIndex` naming it, `no_index_frontier`, `degraded: true` - and a store the profile does NOT have is still refused, by the shared `MailService.DescribeUnresolvedFolderStore`, with the stores that DO exist named. When Outlook cannot be reached the refusal says exactly that rather than claiming the store does not exist. **The scope is never silently widened.** `thread`'s `store` does widen (and reports `scopeWidened`) because there it is only a speed hint - the conversation is pinned by `conversation_id`/`id` either way - but `search`'s `store` is a filter on the result set, so widening it would answer with another account's mail under a scope the caller chose: a wrong answer, not a slow one. `index.storeNotIndexed` exists because `index.rowsScanned: 0` cannot say this - "a statement ran and matched nothing" points at "no such mail", while "no statement ran, and none could have" points at `exhaustive: true`.

**`thread` says when part of the profile is outside both of its tiers** (audit gap C4, closed 2026-08-18). Outlook's `Conversation` object walks the store of the item it was opened from, so a conversation spanning two accounts gets a LIVE check of one and index coverage of the rest. That was already reported as `unwalked_store` - but only when the index held rows from the other store, because the code was raised by comparing the index hits' stores against the walked one. Point it at the profile shape this product keeps meeting, one indexed mailbox plus a data file Windows Search has never opened, and it said nothing at all: the data file contributes no rows to compare against, and half a conversation could be missing under `freshness: "live"` with `degraded` absent. `thread` now also asks OUTLOOK which stores exist and probes each one, through the same `MailService.StoresMissingFromIndex` rule the freshness sweep uses (only a probe's "no" counts; absence from the discovery catalog is never evidence; a store that could not be settled is reported neither way). Stores the index holds nothing for and the walk did not cover are named in `live.storesWithoutIndex` - capped at the same `UnindexedStoreListCap` with the same truncated/total pair - and raise `unindexed_store` in `live.coverageGaps`, `freshness: "partial"` and `degraded: true`. It is a deliberately WEAKER claim than `unwalked_store`, and the advice says so: this one means the question could not be asked, not that the members were checked and found absent. **The anchor's own store is never named**, however unindexed it is - the walk enumerated the conversation there member by member - which is what keeps this from firing on every conversation on a single-PST profile. Cost: one store-list read and one probe per store, both from the five-minute caches `search` already fills, under `StoreIndexProbeBudgetMs`, and only on a walk that ran and returned members.

Term matching (D40, renamed 2026-07-26; cross-column AND added in soak fix 13): `query` terms are whitespace-separated and ANDed, and `search_in` chooses where they must match — `subject_and_body` (default), `subject` or `body`; all three tiers honor it. In the default scope every tier ANDs the terms **across** the parts, one subject-OR-body pair per term (`(CONTAINS(System.Subject, '"a"') OR CONTAINS(System.Search.Contents, '"a"')) AND (CONTAINS(System.Subject, '"b"') OR CONTAINS(System.Search.Contents, '"b"'))`), so a mail carrying one term in the subject and another in the body matches — the in-column shape that shipped until then missed exactly those. Narrowed scopes stay single-column, where an in-column AND is equivalent and cheaper. Measured cost of the pairs on the dev machine (warm best-of-3, agent-sized TOP 26 + ORDER BY): +0-2 ms at 1-3 terms; recall gain on real corpora: `invoice payment` 3817 → 3857 rows, `offerte klant` 1058 → 1093. `System.Search.Contents` is body **plus attachment content**, which is why attachment-content matches only exist in the index tier; the sweep matches `item.Body` and exhaustive matches `urn:schemas:httpmail:textdescription`. That asymmetry decides what the two attachment filters do to the freshness tier (D47): an **attachment-only** request cannot get a single valid row from the sweep, so the sweep is REFUSED and the skip is reported in `advice` — the shape the recipient-filter refusal already had, and coherent with the exhaustive tier, which refuses such a search outright; until soak fix 20 those message rows were merged in regardless, and the filter returned exactly what it excluded. `include_attachment_hits: false` is deliberately NOT symmetric: message rows are what that caller asked for, so the sweep runs untouched. **The DEFAULT case says so too since 2026-08-18** (audit gap B2): any search whose terms go against the body scope carries `sweep.attachmentTextCovered: false`, because the tier responsible for everything newer than the index frontier is the one tier that cannot read an attachment - so a term inside a PDF that arrived four minutes ago is absent from an answer reporting `freshness: "live"`, which is the reading an agent trusts most. The field is never `true` (it states what the tier can do, not what this sweep did) and raises no coverage code, because the condition holds for nearly every search and a permanent `partial` would devalue the flag; the advice sentence is emitted only when the sweep ran AND `sweep.itemsSeen` is non-zero, since a freshness window with no mail in it cannot be hiding anything. Whole-word matching is exact in the index tier; the sweep's re-match is substring by design (deliberate over-match on the freshness window) and exhaustive falls back from `ci_phrasematch` to substring `LIKE` when instant search is off, when `GetTable` rejects the filter, or for prefix (`*`) terms — the runtime surfaces that in `advice`.

## Build and test

Requires the .NET 10 SDK. **Always build by explicit csproj path — never via `OutlookAI.slnx`** (the solution only carries the VSTO add-in, which needs MSBuild + VSTO tooling):

```
dotnet build McpServer/OutlookAI.Core/OutlookAI.Core.csproj -c Release
dotnet build McpServer/OutlookAI.McpServer/OutlookAI.McpServer.csproj -c Release
dotnet test  McpServer/OutlookAI.McpServer.Tests/OutlookAI.McpServer.Tests.csproj --filter "Category!=Live"   # CI-safe tier
dotnet test  McpServer/OutlookAI.McpServer.Tests/OutlookAI.McpServer.Tests.csproj                             # full suite (dev machine)
```

The **shipped** artifact is not a `dotnet build` output — the release workflow publishes it into the installer payload. To reproduce that shape locally:

```
dotnet publish McpServer/OutlookAI.McpServer/OutlookAI.McpServer.csproj -c Release -r win-x64 --self-contained false -o <out-dir>
```

Add `-p:Version=<major.minor.patch.build>` to reproduce the release's version stamp; without it the build carries the `99.99.99.0` developer version from `Directory.Build.props`. See [Deployment and registration](#deployment-and-registration).

Live-test conventions:

- Machine-local identifiers (store display names, a probe term) live in the **gitignored** `OutlookAI.McpServer.Tests/live-fixtures/live-test-settings.json` (`machineProfile`, `testHubStoreDisplayName`, `expectedStoreDisplayNames[]`, `expectedDelegateStoreDisplayNames[]`, `probeTerm`, `subjectOnlyProbe`). The repo is public: account identifiers, live fixtures, audit logs, and screenshots are never committed.
- `machineProfile` says what the machine IS: `Production` (the default, and what an older settings file means) or `Portable`. It decides which blocks are mandatory - the hub and the watched stores everywhere, `probeTerm` and `subjectOnlyProbe` only on `Production`, because both name real mail a dedicated test machine does not have.
- The live tier is split by a second trait. `LiveTier=Portable` (19 of 115 methods) runs on any configured machine; `LiveTier=ProfileBound` (96) needs the maintainer's own profile and carries at least one `Requires` value saying which part of it. `T1/LiveTierInventoryTests` enforces the classification in CI. **How to run either, how to configure a fresh machine, and what to check afterwards: `Docs/live-tier-on-the-vm.md`.**
- All test writes target one designated low-value **test-hub mailbox** (configured in the settings file); other stores are read-only for tests except property-asserted, never-displayed identity checks.
- Every test artifact carries the subject tag `[OutlookAI-McpTest]`; deletion requires BOTH the tag and a this-run EntryID/marker match. Cleanup loops until the zero count is **stable** (self-send copies can materialize after a first pass returns zero) and the suite ends with a cross-account sweep asserting zero tagged items.
- Tests may start Outlook (headless COM start) and drive its UI, but never kill or restart it. Test output never prints subjects/bodies from business stores — counts, ids, hashes, booleans only.
- Tests run sequentially (`xunit.runner.json` disables collection parallelism) so live timing and Outlook interactions stay deterministic. The T3 client locates the built server exe via an `AssemblyMetadata` attribute baked into the tests csproj.

Two T2 tests exist and have never been run, both read-only, both written for questions T1 cannot reach:

- **`LiveResumableScanTests`** is the acceptance for the resumable exhaustive scan (F2). A stand-in session returns whatever a test tells it to, so T1 can pin the token's lifetime, its refusals, the payload and the walk order - but not whether Outlook's folder enumeration is stable, whether `Table.Sort` succeeds, or whether an unsorted table hands back rows in the same order twice. Those three are the ladder's premises. The test that matters is the identity one: the EntryID set of a scan paged at `top: 2` must EQUAL the set from one unpaged run, with no duplicates.
- **`LiveTableSortProbeTests`** settles whether the freshness sweep's sort has EVER applied. Microsoft's `Table.Sort` reference says a sort property may be referenced "by their explicit string names only; cannot reference properties by their namespaces", and `SweepFolder` passes a namespace. It opens one table per store, tries both spellings with the column add and the sort caught separately, reads the FIRST ROW of each, and prints a per-store verdict plus one ANSWER line. Four read-only PowerShell probes could not settle it - every property form and even the no-argument form failed identically with `DISP_E_PARAMNOTOPTIONAL`, which is PowerShell late binding against the `Table` COM object rather than Outlook's verdict, so it needs early-bound C#. Every outcome except "the probe could not run" answers the question, so the only assertion is that it ran.

## Deployment and registration

### Installed mode (the shipping path, Phase 8)

The server ships inside the normal add-in installer. The release workflow publishes it **framework-dependent, `win-x64`** into `publish\McpServer\`, where `Installer.iss`'s single recursive payload rule (`Source: "publish\*" … recursesubdirs`) picks it up, so it lands at:

```
{app}\McpServer\OutlookAI.McpServer.exe        {app} = %LOCALAPPDATA%\OutlookAI\Setup
```

`{app}` is per-user (`PrivilegesRequired=lowest`, no admin for the install itself) and is recorded in `HKCU\Software\OutlookAI\InstallDir`, so the add-in resolves the server from the registry rather than guessing from its own assembly location — installed, that assembly sits under `{app}\Application Files\<version>\`, but in a developer build it sits directly in `bin\Release`.

Framework-dependent is a deliberate choice: self-contained would add ~70 MB and blow past the auto-updater's hard 50 MB download cap (`UpdateService.maxDownloadBytes`, enforced by a release-workflow gate). The prerequisite that buys is the **base** .NET 10 runtime — `Microsoft.NETCore.App` 10.x, **not** the Desktop runtime, since nothing here references WinForms or WPF. Default roll-forward is `Minor`, so any 10.x satisfies it and 11.x would not; both the installer's `IsNetRuntime10Installed` and the add-in's `McpRegistrationService.IsDotnetRuntime10Installed` therefore probe for a `10.` directory specifically, and both probe the **filesystem** (`…\dotnet\shared\Microsoft.NETCore.App`) because the `sharedfx` registry key is absent on machines that do have the runtime. The installer downloads and installs it like it already does for .NET Framework 4.8 and the VSTO runtime — **interactive installs only**: a silent auto-update runs unattended after Outlook closes, and the elevation prompt would sit there unanswered. On that path the add-in detects the missing runtime instead and reports it.

**Both components carry one version.** The release stamps the same `FULL_VERSION` into `Properties/AssemblyInfo.cs` and into the server via `-p:Version=`, and the workflow fails the release if the published exe's `FileVersion` does not match. Local builds of both keep `99.99.99.0` (`McpServer/Directory.Build.props`), which is the marker the add-in's `UpdateService` uses to skip self-updating a developer build.

**Per-session processes and file-in-use.** Claude Code spawns one server process per agent session (it exits on stdin EOF), so several copies typically hold their own image file open when an update lands. `CloseApplications=yes` alone does not deal with them — Restart Manager has no window to ask — so `StopRunningMcpServers` stops them explicitly at `ssInstall`, i.e. **before** any file is replaced, matching on `ExecutablePath` under `{app}`. Matching by path and never by image name is what keeps a developer build running from a source tree alive during an install. A session whose server was stopped simply spawns a fresh one on its next mail call; nothing is persisted in the server process. What that costs the session is the per-process state: hit ids (`h1`, `h2`, …) and send-confirmation tokens are invalidated, and the error text tells the agent to re-search.

### The add-in owns the registration

`Services/McpRegistrationService.cs` (add-in side, net48) owns both scopes. The text surgery is in `Services/McpConfigEditor.cs`, which is **linked into the T1 test project** (see the tests csproj and `T1/McpConfigEditorTests.cs`) — that file edits configuration the add-in does not own, where a bad splice silently costs the user settings they cannot get back, so it is written framework-neutral (no `JavaScriptSerializer`, no `System.Text.Json`) precisely so the unit tier can pin the code that actually ships. Note the consequence for CI: `mcpserver.yml` lists `Services/McpConfigEditor.cs` in its path filters even though the file lives with the add-in.

**User scope is opt-in, and the opt-in is never inferred.** `HKCU\Software\OutlookAI\Mcp\GlobalRegistrationEnabled` is a **tri-state** DWORD: 1 on, 0 off, *absent* never decided. Absent is load-bearing: it is the difference between "the user does not want this" and "the user has not been asked yet", and only the first may be acted on. The rules live in `Services/McpRegistrationDecision.cs` — pure, **also linked into the T1 test project** (`T1/McpRegistrationDecisionTests.cs`, and another `mcpserver.yml` path filter) — as one matrix over (stored intent × what the entry is):

| | no entry | entry is **ours** | entry is **foreign** | unreadable |
|---|---|---|---|---|
| **never decided** | ask (first run) | adopt silently, persist on | ask (replace it, or leave it) | nothing |
| **on** | ask (put it back, or turn off) | keep correct | repoint it | nothing |
| **off** | nothing | ask (remove it, or turn on) | nothing | nothing |

"Ours" is narrow on purpose: a stdio entry whose `command`, once `${VAR}` is expanded, resolves to the installed server (`McpRegistrationService.ClassifyEntry`). Anything else — a wrapper the user registered under that name, a remote entry, a non-object value — is **foreign**, and foreign is untouchable in both directions: never adopted as a silent opt-in, never overwritten, never removed. Removing it would also silently undo the user's own "leave it alone" answer on the very next start.

A question is handed to `TaskPane/McpRegistrationPrompt.cs`, which shows it **only** once Outlook startup has settled and only if this process owns a window a human can see (`IsWindowVisible` + `IsIconic` over its own top-level windows, mirroring `ComposeSurface.CountUserVisibleWindows`). A D17-autostarted headless Outlook therefore asks nothing and **writes nothing** — status `awaiting_choice` — leaving the next interactive session to ask. At most one question per Outlook session, answered or not. While a question is outstanding the reconcile changes nothing at all: no config write, no toggle write.

An answer arrives back as `McpRegistrationService.ApplyUserChoice(bool)` — the same call the settings tick box makes — which persists the preference and reconciles with it treated as *just declared*, so it acts instead of asking again. Once on is written it is sticky in the sense that matters: deleting the entry by hand does not turn the feature off, it raises the "put it back?" question.

While it is on, the reconcile runs on **every Outlook start**, off the UI thread — same shape as `OutlookTuningService`, for the same reason: it heals drift instead of trusting a one-shot install-time write. When it is off, the reconcile *removes* our entry and then leaves the file alone; **turning the toggle off is the deregistration path**, deliberately, instead of an uninstall hook.

The file belongs to the Claude Code CLI, is large, and is rewritten by that CLI, so the discipline is defensive:

- a file that does not parse is **never** written to (a truncating rewrite would cost the user every project entry in it) — it is reported as `config_unreadable`
- only the `mcpServers` value is re-rendered; `McpConfigEditor.TryFindTopLevelValueSpan` locates that span with a direct-member walk that skips each value whole, and every other byte is spliced through unchanged, so no unrelated setting is reformatted or reordered and a nested `mcpServers` key inside a project entry cannot be mistaken for the top-level one
- other servers, and any extra keys on the `outlookai` entry, are carried over verbatim; the entry is normalized to `type: stdio` with `command` = the registered command (plus empty `args`/`env` when absent)
- the result is re-parsed and checked (top-level key count unchanged, the command reads back byte-identical, and *expands* to the installed exe) *before* anything is written
- the write is atomic via `File.Replace`, leaving the previous content as `~/.claude.json.outlookai-backup`
- an already-correct entry is a **no-op** — no write, no backup churn
- removal cuts only our member, its separating comma and its own indentation, and is verified the same way (result parses, our entry gone, every other server and top-level key still present)

**The registered command is the portable form.** `${LOCALAPPDATA}/OutlookAI/Setup/McpServer/OutlookAI.McpServer.exe` — Claude Code expands `${VAR}` and `${VAR:-default}` in `command`, `args` and `env`, in both file shapes. That survives a roaming profile and a renamed account, which is drift the reconcile would otherwise have to keep papering over. `McpConfigEditor.PreferredCommand` falls back to the resolved absolute path whenever the portable spelling does not expand to exactly that file (developer build, non-default install directory), so the entry is never aspirational. Acceptance compares the registered *string* against what we would write, with an equivalent-path escape hatch that is disabled when the portable form is what we would write — which is what upgrades a legacy absolute-path entry to the portable spelling exactly once instead of accepting it forever.

**`type` is optional, on purpose.** A hand-written entry with a `command` and no `type` is a valid stdio server, so it is accepted as-is; requiring an explicit `type` would score every such entry as drift and rewrite the file on every single Outlook start. An entry carrying a `url`/`httpUrl` instead still scores false — taking a remote server over would break it.

It stands down and reports rather than guessing when Claude Code is absent, when no server sits next to the add-in, or when the .NET 10 runtime is missing. Every run records its outcome under `HKCU\Software\OutlookAI\Mcp` (`Status`, `Detail`, `Command`, `ResolvedServerPath`, `Healed`, `LastReconcileUtc`, `GlobalRegistrationEnabled`) — that key is the contract between the add-in and `outlook_health`. Status codes: `ok`, `healed`, `not_registered_by_choice`, `removed`, `claude_code_not_installed`, `server_not_installed`, `dotnet_runtime_missing`, `config_unreadable`, `awaiting_choice`, `error`. Everything is per-user (HKCU + the user profile): no elevation, no COM, no Outlook object model.

The add-in surfaces the same state as a status line in the OutlookAI Settings dialog, whose **Apply now** re-runs the reconcile.

### Project scope (`.mcp.json`)

**Add to a specific project…** in the settings dialog picks a folder and merges the `outlookai` entry into `<folder>/.mcp.json` — `McpRegistrationService.TryRegisterInProject`, built on the same `McpConfigEditor` splice discipline. The container is structurally identical to the top level of `~/.claude.json`, which is why one implementation serves both.

What differs from user scope:

- **merge, never overwrite** — other servers and every other byte survive; a `.mcp.json` that does not parse is refused and reported rather than replaced; an entry that already names this command writes nothing at all, so the button leaves no empty source-control diff
- a file created from scratch is pretty-printed with LF endings (it is normally committed and read in diffs); an entry spliced into an existing file is rendered on one line, reusing the file's own indentation for the line it introduces rather than pretending to know its formatting
- **no backup is left behind.** `File.Replace` still covers the swap, but the backup is deleted once the write is verified — the project's source control is the better undo, and a stray `.mcp.json.outlookai-backup` in someone's repo would show up in `git status`
- **the add-in does not pre-approve anything.** Claude Code prompts the user to approve the servers in a `.mcp.json` the first time it opens that folder. Writing `enabledMcpjsonServers` into their settings to skip that prompt would be the add-in bypassing a security check on the user's behalf — and it does not work in untrusted folders anyway. The dialog explains the prompt instead.
- it is one-shot: nothing reconciles a project file on later Outlook starts

The CLI equivalent is `claude mcp add --scope project outlookai -- "<absolute path to the exe>"`, which is what the dialog's **Copy CLI command** puts on the clipboard. That one deliberately names the real path rather than `${LOCALAPPDATA}`: PowerShell expands `${NAME}` itself, quoted or not, so the portable spelling would reach the CLI blanked out. Claude Code expands it when it *reads* the file, which is exactly why the file the button writes may use it and a shell command may not.

### Developer setup (secondary path)

Building the server and registering the build output by hand still works, and is what contributors do during development and soak:

```
dotnet build McpServer/OutlookAI.McpServer/OutlookAI.McpServer.csproj -c Release
claude mcp add --scope user outlookai <absolute-path-to>\McpServer\OutlookAI.McpServer\bin\Release\net10.0-windows\OutlookAI.McpServer.exe
```

Any MCP client works equivalently — the server speaks MCP over stdio.

A developer **add-in** build resolves no installed server beside it, so the reconcile reports `server_not_installed` and leaves such a registration alone by design. An installed add-in on the same machine is the opposite case — but only while its "all my projects" toggle is explicitly **on**. Then it *will* take the registration over on the next Outlook start (`healed`), which is exactly the drift the feature exists to fix: re-run the `claude mcp add` above to point it back at your build, and expect to do so again after the next Outlook start. Untick the toggle in OutlookAI Settings if you would rather it left your hand-registered build alone. Unticking it removes the `outlookai` entry **only if that entry is the installed server's** — an entry naming your build output is foreign to it and is left where it is, so on a machine that has never been asked (no stored preference) your hand-registered build survives untouched and Outlook asks what to do with it instead. To sanity-check where a live session's server actually came from, call `outlook_health` and read `registration.runningFrom`.

### Server instructions (MCP `initialize`)

`ServerMetadata.Instructions` is returned as the `instructions` field of the MCP `initialize` result. Claude Code injects it verbatim into every session's context at start (a "# MCP Server Instructions" section) — including sessions where tool search defers the tool schemas to name-only — so the agent knows the mail capability exists before any tool is loaded. Keep it short (it is a passive per-session cost; Claude Code cuts it past 2048 UTF-16 code units (measured 2026-08-18, client 2.1.234)) and keyword-rich (tool search matches against it). T3 pins the exact wire string; T1 pins the length budget, the discovery keywords, and that no test canary ever ships.

Nothing user-authored is ever composed into this field, and no tool or parameter description carries writing instructions. That is deliberate: the schema is a client-capped channel (measured 2026-08-18 against Claude Code 2.1.234: a TOOL description over 2048 UTF-16 code units is cut and the rest replaced with a truncation marker; PARAMETER descriptions are not capped by the client at all, though this repo keeps its own house limit on them) and its contents are fixed at compile time, so it can describe what a tool does and how to call it, and nothing that varies with a user's settings.

## Failure payloads: `outcome`, and the rule about what a failure may claim

Every failure comes back as `{"error": {type, reason, outcome, message, advice, ...}}` with `isError: true`. `outcome` was added 2026-08-20 and is the machine-readable answer to the only question a caller has after a failure: **did the thing I asked for take effect?**

| Value | Means | Example |
|---|---|---|
| `unchanged` | The mailbox is exactly as it was, and the code can PROVE it - the refusal was decided before the first mutating call. | every named draft refusal, every "Nothing was sent", the writing-rules gate, `AccountNotFound` |
| `applied` | It DID happen and the effect stands; the failure is downstream of it. | a move whose audit line could not be written, an answer too large to frame over a mutating operation |
| `unknown` | Nobody can state it. | anything raised by a catch-all around a COM sequence, and every operation the COM host was killed during |

Absent means this server is **not stating** an outcome, which is deliberately not the same as `unchanged`. `MoveItemView` carries the same three values per item, because `Ok` is a boolean over a three-valued result and no wording repairs a field.

**The rule for anyone adding a failure message.** A sentence may assert the negative only if it is produced BEFORE the first mutating COM call on that path. That is why the fourteen true claims in the product are true, and it is the whole content of the 2026-08-19 audit: sixteen others had been written next to precondition checks and then attached to catch-alls that wrap the whole sequence. If the classification is not obvious, do not invent a sentence - call `MutationOutcome.DescribeInterrupted(operation)` (or `DescribeAnswerLost` when the work COMPLETED and only the answer was lost), which branches on `ComSessionOperations.IsRetryable`, and add your own remedy clause after it. The remedies differ sharply and are deliberately NOT shared: update means repeat the identical call, send means check the Outbox, create means check Drafts, discard means check Deleted Items, move means find the item first.

Two consequences worth knowing. `ComSessionOperations` fails closed, so a contract method added without a classification produces an over-cautious `unknown` rather than a false `unchanged` - and T1 `SessionRetryClassificationTests` fails the build until it is classified. And T1 `AtomicityClaimsTests` asserts on `advice` as well as `message`: the defect that made this necessary was a correct message travelling beside an advice string that said the opposite, in one payload, with a test watching only the message.

## Load-bearing facts (learned in Phases 1–6; the code comments reference these)

1. **Decoded 24-byte index EntryIDs are NOT openable on cached-Exchange stores** — `GetItemFromID` returns 0x80040107 for every store of this shape. The index URL's value is the store UID + folder segments + timestamp; `HitLocator` maps a hit to the real (~70-byte) EntryID by walking to the folder and probing via `Folder.GetTable` with a DASL subject + received-time window (5 s tolerance for mail, 120 s for attachment rows), tiering down to `Items.Restrict`. Located EntryIDs are cached per process; reads average well under 100 ms.
2. **Index `System.Message.DateReceived` is UTC**; COM `ReceivedTime` is local wall time. Convert deliberately, never compare raw.
3. **Delegate-store hits are indexed under the OWNER's `/1/<delegate name>` subtree** and the URL short id carries the OWNER's store UID — route delegate hits by folder segments, never by UID. Index URL folder segments use localized display names and match COM folder names exactly.
4. **Only per-column `CONTAINS` is index-backed for sender/recipient filters** — `=`/`LIKE` on `System.Message.FromAddress`/`ToAddress` are multi-second property scans. `SCOPE` needs the exact `($hash)` store segment; discover small stores via `CONTAINS(To/From, '"address"')`, not big URL samples.
5. **Late-bound dynamic COM maps failure HRESULTs to plain .NET exceptions** (E_INVALIDARG → `ArgumentException`, binder failures → `RuntimeBinderException`). Catching only `COMException` misses real failures — use `OutlookComSession.IsComCallFailure` for every optional COM path.
6. **A busy Outlook rejects incoming automation calls (`RPC_E_CALL_REJECTED`)** — e.g. right after `Explorer.Search`. The pumped STA registers an `IMessageFilter` that retries every 250 ms for up to 30 s; this protects every gateway call.
7. **`MailItem.SendUsingAccount` is a PROPERTYPUTREF property: a dynamic assignment silently no-ops** and the DEFAULT account would send. Set it via `InvokeMember(..., BindingFlags.PutRefDispProperty, ...)` and verify by getter readback **in the same session** before any `Send()`. Cross-session readback of saved drafts returns null — verify at send time, not after reopen.
8. **Per-account draft filing:** a plain `CreateItem` draft saves into the DEFAULT store's Drafts — create per-account drafts via the target store's `Drafts.Items.Add(0)`. `Reply()`/`ReplyAll()`/`Forward()` + `Save()` land in the source store's Drafts. Threading only ever via those three methods.
9. **The signature `GetInspector` touch leaves a hidden Inspector** inside Outlook — close it (`Close(olDiscard)`) after `Save()` when not displaying. **Word-document edits (the signature-override path) reach the item ONLY via `Inspector.Close(olSave)` on the SAME held inspector** — `item.Save()` does not flush them, an `item.Save()` between the edits and the close re-renders the document from the item and silently wipes them, and closing via a re-acquired inspector reference loses them too (probe-proven).
10. **Sent items get a NEW EntryID** — capture outcome snapshots before `Send()`; verify arrival via the Inbox side (the Sent-copy lags sweep windows).
11. **The audit log is load-bearing:** draft/save/send operations THROW when their audit line cannot be written (the EntryID is preserved in the error text). `send` refuses fail-closed on any token/content/identity mismatch, and recomputes the content hash inside the STA right before sending.
12. **Deleted items keep index rows** (with `IncludeDeletedItems=1`) — live samplers must exclude the test tag; agents should expect the occasional just-deleted hit to fail location with a re-run-search error.
13. **A failed mutating call has usually already mutated something.** `TryCreateNewDraft` commits the item with `Save()` and then does four more COM calls (inspector close, relocate, `Display`, snapshots) inside the same `try`; `TryMoveItemToPath` creates missing folders BEFORE the target guard rejects the destination; `TrySaveAttachment` leaves a partial file when `SaveAsFile` throws; `TryDisplayItem`'s `Display()` is the LAST call in its sequence. Each of those reports the residue on the failure path now (`savedDraftEntryId`, `createdFolderPaths`, `attemptedPath`, and prose respectively) - do not add a step after a mutating call without deciding what the failure path says about it.
14. **Items get a NEW EntryID on ANY move** (`MailItem.Move` returns the moved item — snapshot its EntryID; the old id goes stale, though cached Exchange may keep answering it briefly). **Folder sync-wedge (live-probed):** deleting items while they sit INSIDE a folder marks that folder "synchronizing local changes" on cached Exchange, after which the folder cannot be hard-removed from Deleted Items for the rest of the Outlook session — move items OUT to a permanent folder and delete them there instead; a folder with only move-history removes cleanly (`Folders.Remove` on the Deleted Items copy).
15. **A DASL date literal is parsed in the MACHINE locale, and a wrong one fails SILENTLY** (measured 2026-08-18). Microsoft documents it - "Outlook evaluates date-time values according to the time format, short date format, and long date format settings in the Regional and Language Options applet" - and both formatters shipped the invariant US `MM/dd/yyyy`, so on a day-first box every date with a day of 12 or lower was read with day and month transposed: an exhaustive 1-5 August window returned 121 items from 29 January to 7 June and none from August, and a sweep window that transposed into the future selected nothing while still reporting `foldersSwept` and `freshness: "live"`. Every `DateTime` that becomes a DASL literal now goes through **`Com/DaslDateLiteral.FormatUtc`** - year-first `yyyy-MM-dd HH:mm:ss`, the same shape `WsSqlBuilder` emits for WS-SQL, unambiguous under any locale and pinned in T1 under five thread cultures. Never format one in the current culture (correct only while the process culture equals the Windows user locale) and never use ISO-8601 with a `T`: `2026-08-01T00:00:00` does not throw, it silently matches the whole folder. `Folder.GetTable` and `Items.Restrict` accepted exactly the same format set, row for row.

## Health & diagnostics

`outlook_health` reports everything the server depends on (Outlook process/version/Office major/headless state, probed COM liveness, store reachability, index freshness globally AND per store with actionable advice, WSearch service state, audit writability, tuning state, installer mutex) without ever starting Outlook — it merges the former `health` and `index_status` tools into one call. The audit log at `%LOCALAPPDATA%\OutlookAI\audit.log` records every write operation with timestamps and EntryIDs.

**`outlook.officeVersion`: which Office registry hive every registry-backed answer came out of.** Office keeps per-user state under `HKCU\Software\Microsoft\Office\<major>\`, and the major is not inferable: `16.0` is Outlook 2016 through Microsoft 365, `15.0` is 2013, `17.0` is whatever comes next. The server used to hardcode `16.0` in four places - the Outlook Search user key, that key's Policies mirror, and the profile-registry root behind `list_accounts` and the signature defaults - so on a 15.0 or 17.0 machine it read hives Outlook never writes and reported empty accounts, empty signature assignments and a default-looking search backend. Every one of those is a plausible answer on a healthy machine, which is what made it invisible.

It is now detected once per process from whichever `HKCU\Software\Microsoft\Office\<major>\Outlook` key is a **real Outlook hive**, probed newest first (`16.0`, `17.0`, `15.0` - so a machine with two Office versions is treated as the newer). The detection is the add-in's: `Services\OfficeVersions.cs` is **linked** into `OutlookAI.Core` rather than reimplemented, so both halves probe the same versions in the same order by construction (same trick as `Services\AddInServerContract.cs`; it has to stay `internal`, or the two compiled copies collide as CS0436). `OutlookProfileRegistry` re-exports the list, the fallback, the detected value and the hive rule for callers outside Core.

**"Real Outlook hive", not "the key exists" - and the difference is the whole feature.** `Installer.iss` writes a resiliency exemption under `...\Office\{16.0,15.0,17.0}\Outlook\Resiliency\DoNotDisableAddinList` on every install, deliberately, so the add-in survives a slow start on whichever Outlook is actually there - and writing that value creates the entire path above it. So **on every machine this product is installed on, all three Outlook keys exist**, and a bare key-exists probe answers `16.0` (the first version tried) on an Outlook 2013 machine just as confidently as on a 2016 one. Measured on the dev machine 2026-08-17: the `15.0` and `17.0` keys each held exactly one subkey (`Resiliency`) and no values, while the real `16.0` key held 31 subkeys and 4 values including `DefaultProfile` and `Profiles`. The rule (`OutlookProfileRegistry.IsOutlookHive`, T1-pinned against those measured shapes) is therefore: at least one value, or at least one subkey that is not `Resiliency`.

`officeVersion` is **omitted when none of the supported majors is registered**, and `problems` then says so in words: what it looked for, which hive it fell back to, and that accounts and signature defaults can therefore come back empty on a perfectly healthy Outlook. That sentence is `HealthReporting.NoOfficeVersionProblem`, built from the supported list so it cannot go stale.

The **`registration`** block (Phase 8, `HealthReporting.ReadMcpRegistration`) answers "is this server the one Claude Code is configured to spawn?":

| Field | Meaning |
|---|---|
| `status` | `ok` (the registered command IS this executable), `drifted` (registered, but naming something else — typically a stale developer build path), `absent` (no `outlookai` entry), `unreadable` (config present but not parseable, so the add-in never rewrites it), `unknown` (config could not be examined) |
| `runningFrom` | The executable hosting this process (`CurrentProcessPath()` — not `Environment.ProcessPath`, which does not exist on the net48 target Core also compiles for) |
| `registeredCommand` | `mcpServers.outlookai.command` as read from `~/.claude.json`, verbatim — including a `${LOCALAPPDATA}/…` form, which `status` expands before comparing (`HealthReporting.ExpandEnvironmentReferences`, the read-side twin of the add-in's writer) |
| `addInStatus`, `addInHealed`, `addInLastReconcileUtc`, `addInResolvedServerPath` | What the add-in's last reconcile recorded under `HKCU\Software\OutlookAI\Mcp`; null when the add-in has never run one |

`status` is computed by comparing `registeredCommand` against `runningFrom` (path comparison, not string comparison — casing and separators may differ for the same file), so drift is visible **even when the add-in has never reconciled**, and the two halves of the block can legitimately disagree: that disagreement is the signal. Health only ever *reports* on `~/.claude.json` — it never reads it for writing and never repairs it. Repair is the add-in's job.

The tuning block of `outlook_health` also carries `uiSearchBackend` — the EFFECTIVE Outlook UI search backend read from the live registry (`DisableServerAssistedSearch`, policy hive authoritative over the user hive; absent/0 = Outlook's server-assisted default). `"local"` means the Outlook search box queries the same Windows Search index the agent's `search` uses; `"server-assisted"` means UI results are server-capped and differently ranked, so what the user sees can diverge from what the agent finds — `show_search_results` then appends a strong advice note recommending the Search tuning group be re-enabled. The registry value stays deliberately user-togglable: disabling it is the sanctioned mitigation for the documented replies-stick-in-Outbox side effect of local-search mode.
